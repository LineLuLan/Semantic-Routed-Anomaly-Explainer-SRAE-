# Semantic-Routed Anomaly Explainer (SRAE)

> Detect anomalies in business time-series data, route each anomaly to
> the closest matching playbook via vector cosine similarity, and turn
> the pair into a one-paragraph on-call report with an LLM. One click
> in the UI runs all three pipelines.

## Why this exists

A small SRE team has time-series metrics (`traffic`, `sales`, `error_rate`, …)
in a database, plus a Confluence page of "if this happens, do this"
playbooks. When something breaks at 2 AM, the on-call engineer has to:

1. Spot the anomaly on a Grafana dashboard.
2. Skim the playbook page and find the matching scenario.
3. Type a one-paragraph summary into the on-call channel for context.

SRAE collapses all three steps into a single `Analyze` button. It's a
**local-first** MVP — no cloud, no Docker, just Python + Node + Postgres
on your laptop.

## Architecture

```
┌──────────────┐    ┌──────────────────┐    ┌───────────────────┐    ┌──────────────┐
│  Postgres    │    │  AnomalyDetector │    │  SemanticRouter   │    │  Explainer   │
│  srae DB     │───▶│  IsolationForest │───▶│  ChromaDB cosine  │───▶│  Groq Llama  │
│  504 rows    │    │  (per metric)    │    │  k-NN over 6 rules│    │  3.1-8b      │
└──────────────┘    └──────────────────┘    └───────────────────┘    └──────────────┘
                                                                              │
                                                                              ▼
                              ┌──────────────────────────────────────────────────┐
                              │  FastAPI  /health  /analyze  /timeseries         │
                              └──────────────────────────────────────────────────┘
                                                  ▲
                                                  │ fetch (CORS)
                              ┌──────────────────────────────────────────────────┐
                              │  Next.js 16 dashboard at http://localhost:3000   │
                              │  Hero + status strip + chart + anomaly cards     │
                              └──────────────────────────────────────────────────┘
```

Two stores, one purpose each:
- **Postgres** owns relational time-series (`time_series_data` table).
- **ChromaDB PersistentClient** (file-based at `.chroma/`) owns rule
  embeddings (`business_rules` collection, 384-dim vectors normalized).

> **Why not pgvector?** PostgreSQL 18 on Windows ships without pgvector
> binaries and installing it requires Visual Studio Build Tools or
> admin-rights binary copy. We pivoted to ChromaDB on 2026-04-25 — see
> `PLAN.md` §10. The `SemanticRouter.route()` I/O contract is unchanged.

## Tech stack

| Layer | Tech | Notes |
|---|---|---|
| Database | PostgreSQL 18 | local install, no Docker |
| Vector store | ChromaDB ≥ 0.5 | PersistentClient at `.chroma/` |
| ML | scikit-learn ≥ 1.5 | `IsolationForest` per metric, hour-of-day feature |

| Charts | recharts 3.8 | line chart with reference dots for anomalies |
| Styling | Tailwind CSS 4 | CSS-first `@theme inline` config |

(OLED)" aesthetic, amber primary `#D97706` + indigo accent `#6366F1` on
slate-900 background, Fira Sans body + Fira Code mono.

## Quick start

### 1. Prerequisites

- **Python 3.11+** (tested on 3.13).
- **Node.js 20+** (tested on 22).
- **PostgreSQL 14+** running locally on `:5432`.
- **Groq API key** (free at https://console.groq.com/keys) — optional,
  the LLM has a `mock=True` path for offline use.

### 2. Create the database

```bash
# Replace <pwd> with your local postgres password
psql -U postgres -h localhost -c "CREATE DATABASE srae;"
```

No extension needed — pgvector was retired in favour of ChromaDB.

### 3. Clone, venv, install Python deps

```bash
git clone https://github.com/LineLuLan/Semantic-Routed-Anomaly-Explainer-SRAE-.git
cd Semantic-Routed-Anomaly-Explainer-SRAE-

python -m venv .venv

# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

pip install -r requirements.txt
```

Total install: ~1.4 GB (torch, sentence-transformers, chromadb).

### 4. Configure secrets

```bash
cp .env.example .env
```

Edit `.env`:

```ini
POSTGRES_URL=postgresql+psycopg2://postgres:<your-pwd>@localhost:5432/srae
GROQ_API_KEY=gsk_<your-key>
GROQ_MODEL=llama-3.1-8b-instant
EMBEDDING_MODEL=sentence-transformers/all-MiniLM-L6-v2
LOG_LEVEL=INFO
```

### 5. Seed the data

Two seeds, one each store:

```bash
# Postgres time-series (504 rows: 7 days × 24 hours × 3 metrics, 3 injected anomalies)
python -m src.db.seed

# ChromaDB business rules (6 playbooks, encoded with all-MiniLM-L6-v2)
python -m src.router.seed_chroma
```

`src/db/seed.py` is idempotent — it truncates the table on every run.
`src/router/seed_chroma.py` drops + recreates the collection.

### 6. Install Next.js deps

```bash
cd webui
npm install
cd ..
```

### 7. Run both servers

```bash
# Terminal 1 — API
.venv/Scripts/python.exe -m uvicorn src.app.api:app --reload

# Terminal 2 — UI
cd webui && npm run dev
```

Open **http://localhost:3000**.

## How to test the MVP

The MVP is a single-page dashboard. Below is what to click, what to type
(if anything), and what you should see.

### A. Smoke test the UI manually

1. Open http://localhost:3000.
2. **Status strip** at the top should read:
   - `Status: ok`
   - `Postgres: online`
   - `Chroma: ready`
   - `Groq: configured` (if you put a key in `.env`) or `off` (mock mode).
3. **Time-series chart** shows three coloured lines for traffic / sales /
   error_rate over the seeded week. No red dots yet.
4. **Toggle "Mock LLM"** if you want a fast/free run (no Groq calls).
5. **Click "Analyze"** (the amber button).
6. Watch the chart — three obvious red dots appear at:
   - `2026-04-20 02:00 UTC` — traffic = 5000 (late-night spike)
   - `2026-04-22 11:00 UTC` — sales = 5 (business-hours collapse)
   - `2026-04-23 15:00 UTC` — error_rate = 12.5 (API spike)
   plus several borderline points (contamination = 0.05).
7. **Anomaly cards** appear underneath, each containing:
   - Metric badge + status badge + cosine distance.
   - Value + timestamp.
   - **Matched playbook** (rule_text from ChromaDB).
   - **Suggested action** (metadata).
   - **On-call report** — a paragraph from Groq, or a deterministic
     `[MOCK] …` template if Mock LLM is on.

### B. Test the API directly with `curl`

#### Health check

```bash
curl -s http://localhost:8000/health | python -m json.tool
```

Expected:

```json
{
  "status": "ok",
  "postgres": true,
  "chroma": true,
  "groq_configured": true
}
```

#### Run analysis with the mock LLM (fast, deterministic, no Groq cost)

```bash
curl -s -X POST "http://localhost:8000/analyze?mock=true&limit=3" | python -m json.tool
```

Expected shape: `total_anomalies: 27, returned: 3, mock_llm: true,
reports: [...]` — each report has `timestamp`, `metric`, `value`,
`status`, `rule_text`, `suggested_action`, `distance`, `explanation`.

#### Run analysis with the real Groq LLM

```bash
curl -s -X POST "http://localhost:8000/analyze?mock=false&limit=1" | python -m json.tool
```

Expected: `mock_llm: false`, `explanation` is a 3-5 sentence English
paragraph written by Llama-3.1-8b-instant. Each call costs roughly
1k–2k input tokens.

#### Pull raw time-series for charts

```bash
curl -s "http://localhost:8000/timeseries?metric=traffic&limit=10" | python -m json.tool
```

Expected: `points: [...]` of length 10, each `{timestamp, metric, value}`.

### C. Test each module standalone

```bash
# Phase 1 — DB
pytest tests/test_db.py -v

# Phase 2 — ML
pytest tests/test_ml.py -v
# Verifies the detector flags the 3 injected anomalies exactly.

# Phase 3 — Router
pytest tests/test_router.py -v
# Verifies "Late-night traffic spike at 2 AM" routes to the bot-scraping rule.

# Phase 4 — LLM
pytest tests/test_llm.py -v
# Mock tests always pass. Live Groq test runs only if GROQ_API_KEY is set.

# Phase 5 — App
pytest tests/test_app.py -v
# TestClient drives /health, /analyze, /timeseries, CORS preflight.

# Everything
pytest tests/ -v
# 21 passed, 1 skipped (the "missing key" test, which can't run when key is set).
```

### D. Test the UI build

```bash
cd webui
npm run lint     # ESLint, should be clean
npm run build    # Next 16 production build, should succeed in ~10s
```

### E. Test the input boundary cases

| Scenario | What to do | Expected |
|---|---|---|
| Postgres offline | `pg_ctl stop` (or kill service) | `/health` → `postgres: false`, `/analyze` → 500 from get_session |
| Chroma collection missing | `rm -rf .chroma` | `/health` → `chroma: false`; `/analyze` → 503 with seed instruction |
| GROQ_API_KEY unset | Comment line in `.env` and restart uvicorn | `/health` → `groq_configured: false`; UI auto-defaults to Mock LLM |
| Wrong Groq model | Set `GROQ_MODEL=llama3-8b-8192` (decommissioned) | Live LLM test fails with `400 model_decommissioned` — switch back to `llama-3.1-8b-instant` |
| Empty time-series | `psql -d srae -c "TRUNCATE time_series_data"` | `/analyze` → `total_anomalies: 0, reports: []`; UI shows "system is healthy" |
| Limit clamp | `?limit=999` | API caps at 100, returns top-100 anomalies |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `cannot reach Postgres` on seed | Server not running, or wrong `POSTGRES_URL` | `pg_isready -h localhost`; verify `.env` |
| `ERROR: extension "vector" is not available` | Old schema with pgvector — should be gone after pivot | `git pull` and re-seed; if you forked before 2026-04-25, see `PLAN.md` §10 |
| `400 model_decommissioned` from Groq | Groq retired your model | Update `GROQ_MODEL` in `.env` (currently `llama-3.1-8b-instant`) |
| `/analyze` returns 503 with "SemanticRouter unavailable" | Chroma collection missing | `python -m src.router.seed_chroma` |
| Pyarrow access violation warning | sklearn ↔ pyarrow load order quirk on Windows; harmless | Tests still pass, ignore |
| `Port 3000/8000 in use` | Old dev server alive | `Get-NetTCPConnection -LocalPort 3000` (PowerShell) → `Stop-Process -Id <PID>` |
| `Module not found: chromadb` | venv not activated, or worktree junction broken | Activate `.venv`, or recreate junction (see `PARALLEL_WORKFLOW.md`) |
