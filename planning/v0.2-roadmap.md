# SRAE — v0.2 Roadmap

> **Status of v0.1:** Shipped end-to-end on 2026-04-25. Postgres + ChromaDB +
> sklearn + Groq + FastAPI + Next.js. 21 tests green. Live demo working
> on `localhost:3000` with real Groq Llama-3 reports.
>
> **What v0.2 is for:** harden the routing quality, add CI, make the
> dashboard nicer, and start treating SRAE as a real internal tool not
> a demo.

---

## Guiding principles for v0.2

1. **Tighten the loop, don't widen it.** Don't add features until the
   existing pipeline is reliable enough to demo to a real on-call team.
2. **Quality over breadth on rules.** A tighter 6-rule catalog beats a
   sloppy 30-rule one.
3. **Keep it local-first.** v0.2 still runs on a laptop. Cloud deploy
   is v0.3+.
4. **Tests are the contract.** Every behavioural change ships with a
   test that would have caught its absence.

---

## Workstream A — Routing quality (HIGH priority)

The current cosine matches sit at 0.5–0.6, which is too loose for
real on-call use. v0.2 must produce either a confident match or an
honest "no match".

### A1. Distance threshold + null-route handling

- Add `min_distance: float = 0.45` to `SemanticRouter.route()`.
- If the best cosine distance exceeds the threshold, return
  `{"rule_text": null, "suggested_action": null, "distance": d}`.
- Update `Explainer` to handle null rule by writing a "no playbook
  match — manual triage required" paragraph.
- Update `AnalysisReport` Pydantic model: `rule_text` and
  `suggested_action` become optional.
- UI renders unmatched anomalies with a different card style (no
  amber/indigo accent).

**Effort:** ~1 hour. Owner: 1 dev. Risk: low (behind a default-on flag).
**Tests:** add `test_unmatched_query_returns_null` in `test_router.py`
and `test_analyze_handles_null_route` in `test_app.py`.

### A2. Rule catalog expansion

- Add 6 more rules covering the obvious gaps: cache-stampede,
  third-party-API-down, deploy-rollback-stuck, abuse/DDoS,
  feature-flag-misfire, scheduled-maintenance-bleed.
- After adding, re-run the test corpus:
  ```
  python -m src.router.seed_chroma
  pytest tests/test_router.py -v
  ```
- Expect tighter average distance (< 0.40 on the seed anomalies).

**Effort:** ~1 hour to write rules + verify. Risk: low.

### A3. Cross-encoder rerank (stretch)

- Top-3 candidates from cosine → rerank with
  `cross-encoder/ms-marco-MiniLM-L-6-v2`.
- Adds ~200 ms per query but typically tightens match by 0.1–0.2.
- Behind a `RERANK=true` env flag so it doesn't slow CI.

**Effort:** half a day. Risk: medium (model load size, init time).
Defer if A1 + A2 are enough.

## Workstream B — Operational hardening (HIGH priority)

### B1. GitHub Actions CI

`.github/workflows/ci.yml` runs on every push + PR:

```yaml
- name: Python tests
  run: |
    pip install -r requirements.txt
    # Skip DB-backed tests in CI by not seeding Postgres
    pytest -v -m "not requires_db"

- name: Frontend build
  working-directory: webui
  run: |
    npm ci
    npm run lint
    npm run build
```

- Add a service container for Postgres + a step that runs
  `python -m src.db.seed` to also exercise the `requires_db` tests.
- Add a status badge to the README.

**Effort:** ~1 hour first time, < 10 min thereafter. Risk: low.

### B2. Dependency pinning

Currently `requirements.txt` uses minimums (`>=`). Pin to specific
versions for reproducible CI:

- Generate `pip freeze > requirements.lock` post-install.
- Use `requirements.lock` in CI; keep `requirements.txt` for human
  reading.

**Effort:** 15 minutes. Risk: low.

### B3. Docker Compose for one-command setup

`docker-compose.yml`:
- `postgres:18` service with `srae` DB pre-created via init script.
- Volume-mount `.chroma/` and `.env`.
- App service running the FastAPI app.
- Optional `ui` service running `next start`.

**Effort:** 1–2 hours. Risk: medium (Windows volume mount quirks).
Pays back fast on onboarding.

### B4. Observability

- Add a simple request log to FastAPI: `(timestamp, endpoint, ms,
  status)` to a JSONL file or Postgres table.
- Histogram of `/analyze` latency, count of Groq vs mock calls.
- No fancy Prometheus yet — flat-file or a third Postgres table.

**Effort:** 2 hours. Risk: low.

## Workstream C — UI polish (MEDIUM priority)

### C1. Real browser smoke test

- Wire `playwright` into `webui/`.
- Single test: open `/`, wait for status strip green, click `Analyze`,
  assert at least one anomaly card appears with `[MOCK]` text.
- Run in CI as a separate job (skip if no display server available).

**Effort:** ~2 hours. Risk: medium (Playwright install size).

### C2. Stream reports as they complete

- Switch `/analyze` to SSE: emit one `AnalysisReport` per Groq call
  finishing.
- UI renders cards as they stream in, with a per-card spinner before
  the LLM completes.
- Better UX for `limit=10` with real Groq (currently 5+ seconds blank).

**Effort:** half a day. Risk: medium.

### C3. Keyboard shortcuts

- `Cmd/Ctrl+Enter` triggers Analyze.
- `Cmd/Ctrl+M` toggles mock mode.
- Shortcuts hint shown in a tooltip on the button.

**Effort:** 30 minutes. Risk: trivial.

### C4. Mobile layout pass

- Test at 375 / 768 / 1024 / 1440. Cards probably need to stack at
  768; chart may need horizontal scroll on 375.
- Use `@container` queries (Tailwind 4 supports them).

**Effort:** 1 hour. Risk: low.

## Workstream D — Data + replay (MEDIUM priority)

### D1. Replace mock seed with real ingestion script

- `scripts/ingest_from_csv.py` reads a CSV with columns
  `(timestamp, metric_name, value)` and inserts into
  `time_series_data`.
- Document expected CSV format in README.

**Effort:** 1 hour. Risk: low.

### D2. Time-window query param

- Currently `/analyze` runs the detector over the full table.
- Add `?since=ISO&until=ISO` to scope to a window. Useful when the
  table grows beyond demo size.

**Effort:** 30 minutes. Risk: low.

### D3. Persist anomaly history

- New table `analysis_runs(id, ts, params jsonb, total_anomalies, returned)`
  + `analysis_reports(run_id, ...)`.
- `/analyze` writes a row per run; `/analyze/history` returns recent runs.
- UI gets a "Recent runs" sidebar.

**Effort:** half a day. Risk: medium.

## Suggested execution order

If you have **2 hours**: A1 + A2 + B1.  
If you have **1 day**: above + B3 + C1.  
If you have **a week**: everything except A3 + C2 + D3.

A1 and B1 are the highest-leverage items and should land first. A1
because the routing quality is the biggest credibility issue when
demoing; B1 because every other change is risk-free once CI runs.

---

## Out of scope for v0.2

- Multi-tenant / RBAC.
- Cloud deployment (k8s, ECS, Vercel).
- Vector DB other than Chroma.
- LLM provider other than Groq.
- Real-time streaming ingestion (Kafka, Pub/Sub).
- Autonomous remediation (run the suggested action automatically).

These are v0.3 conversations.

---

## Backlog (parking lot)

- Multi-language playbook support (multilingual embedding model).
- Confidence calibration: turn cosine distance into `low/med/high`
  confidence bands surfaced in the UI.
- Slack / PagerDuty webhook on each report.
- "Why did this match?" debug view: top-3 candidates with distances.
- Replay a historical incident to re-test rules / prompts.
- LLM-as-judge eval harness for explanation quality.
